# Greenmask + n8n: анонимизация PostgreSQL с LLM-парафразом

Тестовый проект демонстрирует сквозной пайплайн анонимизации демо-базы
PostgreSQL (`sanitize_demo`): структурированные PII-поля (email, телефон,
ИНН, номера счетов) маскируются декларативными трансформерами Greenmask, а
неструктурированный свободный текст (заметки менеджеров, комментарии к
платежам) переформулируется через LLM с сохранением смысла, но без
коммерчески чувствительной конкретики. Результат восстанавливается в
отдельную схему `sanitize_demo_target` и проходит независимую
LLM-верификацию на отсутствие остаточных PII-паттернов.

## Выбор инструментов (продуктовая перспектива)

Ниже — обоснование ключевых технических решений с точки зрения того, какую
задачу они решают для бизнеса, а не только "потому что удобно разработчику".

### Почему Greenmask, а не альтернативы

| Greenmask (open source) | Выбран как оптимальный баланс: готовые декларативные трансформеры (Hash, NoiseNumeric, NoiseDate, RandomPerson и т.д.), поддержка кастомных трансформеров через Cmd (что и дало возможность встроить LLM), активная разработка, бесплатная лицензия, конфигурация как код (config.yml можно версионировать в git и ревьюить как обычный PR) |

Ключевой продуктовый аргумент: Greenmask даёт **декларативный, воспроизводимый
и версионируемый** процесс анонимизации — правила анонимизации хранятся в
`config.yml` рядом с кодом, а не "в голове у того, кто писал скрипт когда-то".
Это критично, если анонимизированные дампы регулярно используются командой
QA/аналитики и правила должны эволюционировать вместе со схемой БД.

### Почему PostgreSQL, а не MySQL

Изначально рассматривались обе СУБД, поскольку сам подход (dump → transform →
restore) применим к любой реляционной базе. Решающими для выбора PostgreSQL
стали два практических фактора:

1. **Существующая инфраструктура.** На личном облачном VPS уже развёрнут стек
   сервисов на базе PostgreSQL (в том числе сам n8n использует Postgres как
   бэкенд для хранения workflow и executions) — использование уже
   поднятого PostgreSQL вместо развёртывания отдельного инстанса MySQL с нуля
   позволило уложиться в ограниченные сроки тестового задания, не тратя время
   на настройку параллельной СУБД, которая нигде больше в инфраструктуре не
   используется.
2. **Зрелость инструмента анонимизации именно под Postgres.** Greenmask
   изначально спроектирован и лучше всего поддерживается именно для
   PostgreSQL (native pg_dump/pg_restore формат, логическая репликация типов
   данных, custom types) — аналогичный инструмент для MySQL либо отсутствует,
   либо значительно менее зрелый, что означало бы более высокий риск для
   срока сдачи тестового задания.

### Почему n8n

| n8n (open source, self-hosted) | Уже развёрнут на собственном VPS для других задач, low-code визуальный конструктор ускоряет итерации над промптом и логикой без передеплоя кода, встроенная поддержка Webhook + LLM-нод + условной логики закрывает 100% требований данной задачи |

Продуктовый аргумент: n8n даёт **быструю итерацию над бизнес-логикой**
(промпт для LLM, правила аудита) без участия разработчика на каждое
изменение -- аналитик или продакт-менеджер может сам подправить промпт в
визуальном редакторе, не трогая код Python-скрипта Greenmask.

### Зачем здесь вообще LLM

Классические трансформеры (regex-маскировка, замена на случайные значения)
хорошо работают для **структурированных** полей (email, телефон, ИНН,
суммы) — там заранее известен формат данных. Но свободный текст
(`internal_note`, `comment`) — это неструктурированные бизнес-заметки
произвольной длины и стиля, где конкретика (проценты скидок, суммы штрафов,
детали санкций) вплетена в естественный язык без предсказуемого паттерна.

LLM решает здесь конкретную продуктовую проблему: **сохранить
информационную ценность демо-данных для тестирования UI/аналитики, но
убрать коммерчески чувствительную конкретику**. Простое удаление или
маскировка текста ("[REDACTED]") сделало бы демо-датасет бесполезным для
проверки, например, как выглядит карточка контракта в интерфейсе с реальным
комментарием менеджера. LLM-парафраз — компромисс между "приватно" и
"выглядит как настоящие данные", что важно именно для демо-стендов и
тестовых окружений, которые показываются потенциальным клиентам или новым
сотрудникам без доступа к продакшену.

Дополнительно LLM используется во втором workflow (`audit-text`) как
**независимый контролёр качества** — та же технология, что генерирует
парафраз, применяется повторно в роли аудитора, оценивающего результат
свежим взглядом, без знания исходного текста. Это тот же принцип, что
"второй ревьюер не должен быть автором кода" — снижает риск, что одна и
та же логика "не увидит" собственную ошибку.
